# R2 독립 합성 평가 corpus

이 corpus는 엔진 코드와 기존 탐지 시험을 읽지 않고 작성한 합성 Python 표본이다.
실제 기관 코드, 개인정보, 사람이 수행한 독립 검증 결과가 아니다.
독립성은 기존 구현·시험과 분리된 정답 작성 절차를 뜻한다.
fixture의 source는 평가 입력이며 엔진의 안전성이나 성능 증거가 아니다.

## 고정 분할과 정답

| 분할 | 지원 위험 | 지원 안전 | 미지원 위험 | 미지원 안전 | 전체 |
| --- | ---: | ---: | ---: | ---: | ---: |
| dev | 24 | 24 | 6 | 6 | 60 |
| holdout | 16 | 16 | 4 | 4 | 40 |
| 전체 | 40 | 40 | 10 | 10 | 100 |

위험 50개와 안전 50개를 포함한다. 모든 source와 ID는 서로 다르다.
각 표본은 문법상 유효한 독립 Python 모듈이며 실행하지 않는다.
외부 import와 decorator는 미지원 경계를 표현하는 합성 이름이다.
모든 표본에 SYNTHETIC 표식이 있다. 식별 가능한 실제 값은 사용하지 않는다.

`expected_risk`는 선언된 데이터 흐름과 계약에 따른 노출 위험 정답이다.
`target_support`는 구현 결과를 보기 전에 정한 목표 지원 범위다.
안전 정답이더라도 미지원이면 검토가 필요하다.
위험 정답은 지원 여부와 무관하게 allow로 빠지면 안 된다.
정답과 지원 표시는 결과에 맞춰 바꾸지 않는다. 오류 의심은 별도 검토 후 변경 이유를 기록한다.

## 목표 지원 범위

제한된 Python 순차 대입, 별칭, 중첩 컨테이너와 선택, 문자열 결합·포맷,
로그 인수·extra, logging 표준 모듈·별칭·가져온 메서드·getLogger,
단순 if 합류, 같은 파일의 정적으로 호출되는 private helper,
일반 try/except의 본문·예외·traceback 로그를 포함한다.
외부 decorator, 동적 호출, 클래스, 반복문, comprehension, lambda,
계약을 정적으로 확인할 수 없는 외부 transform·wrapper는 미지원이다.
미지원 예제의 외부 계약은 정답 설명용이며 분석기의 신뢰 등록이 아니다.

요청 본문·JSON·form·data와 payload/body/data/citizen/form/token/phone 인수는
합성 민원 또는 비밀 데이터 source로 가정한다. 상수 문구도 함께 넣어 이름 검색 편향을 줄였다.
단순 이름 변경은 정제가 아니다. body를 request_id로 바꾼 위험 표본도 포함한다.

안전 표본의 request_id는 서버가 별도로 만든 불투명 상관 ID라는 명시적 계약을 가진다.
operation, result_code, status는 서버의 고정·허용 목록 메타데이터다.
이 가정은 평가 계약이며 실제 기관에서 이름만으로 출처를 신뢰하라는 의미가 아니다.
기관 적용 시 생성 경로·실제 호출 계약 확인이 별도로 필요하다.

private helper의 안전 정답은 decorator·동적 export가 없고, 같은 파일에 보이는 정적 호출만
가능한 폐쇄 범위 가정에 의존한다. 인수 이름만으로 helper를 안전하다고 표시하지 않는다.
감사 이벤트 예제는 필요한 이벤트와 메타데이터를 유지하면서 원문은 로그에서 제외한다.
traceback 위험 표본은 예외 메시지에 원문을 넣은 뒤 traceback을 출력한다.
exc_info=False인 안전 표본은 원문 예외 메시지와 traceback을 출력하지 않는다.

## 평가와 보류 규칙

초기 개발에는 dev만 사용했다. 최초 holdout은 탐지 구현을 동결한 뒤 평가했다.
그 결과를 진단에 사용한 뒤에는 최초 holdout을 새로운 최종 평가로 부르지 않는다.
최초 100개 전체 수, 80% 목표 지원 비율, 분할별 결과, 오류·검토 필요 비율을 함께 보고한다.
지원 80개를 대상으로 위험 40개의 탐지 재현율과 안전 40개의 오탐률을 산출한다.
미지원 20개를 분모에서 숨기지 말고 별도 검토·오류·위험 탐지·allow 수를 보고한다.
검토 필요를 위험 탐지 성공으로 합산하지 않는다. 목표는 지원 재현율 95% 이상,
지원 안전 오탐률 5% 이하이며 위험 allow는 확대 적용 중단 조건이다.

최초 동결 시 두 파일의 SHA-256:

- dev: `112bf8768c89b0744c38f18c65930f034b93076601ff2fa6b0c0c364527a5531`
- holdout: `c330111ec93c1003a16c66ee01fb171455f5c22ffed8ff96b468f98442af9123`

작성 시 JSON 구조·정확한 필드·ID 유일성·source 유일성·분할/정답 수를 확인하고
100개 source를 ast.parse로 검사했다. 탐지 결과를 읽거나 정답을 결과에 맞추지 않았다.


## 후속 확인용 holdout: 최초 평가와 분리

최초 holdout은 안전한 예외 처리 경로의 과도한 검토 요구 때문에 완료 기준에 미달했다.
실행 담당자가 전달한 기록은 지원 32개 중 6개 검토 필요, 즉 18.75%로,
고정된 검토 필요 상한 10%를 초과했다. 이 기록은 corpus 작성자가 독립 실행으로 확인한 결과가 아니다.
이후 오류 종류를 구현 수정에 사용했으므로 최초 holdout 40개는 진단 표본으로 남긴다.
원래 dev·holdout 파일과 정답은 변경하지 않았다. 상한을 결과에 맞춰 낮추지 않는다.

`tests/fixtures/evaluation_confirmatory.json`은 해당 수정 후 다시 동결한 탐지기를
평가하기 위해 새로 작성한 확인용 표본이다. 구현 담당자에게 source를 공개하지 않고 작성했다.
검사기의 구현과 평가 보고 코드를 읽지 않았다. 기존 100개는 구조적 중복 검사에만 사용했다.
이 문서는 새 표본의 탐지 결과나 완료 기준 통과를 주장하지 않는다.

| 분할 | 지원 위험 | 지원 안전 | 미지원 위험 | 미지원 안전 | 전체 |
| --- | ---: | ---: | ---: | ---: | ---: |
| confirmatory | 16 | 16 | 4 | 4 | 40 |

파일의 형식은 `govcode-evaluation-v1`이고 기존 평가기 계약에 맞춰 `split`은 `holdout`이다.
ID 접두사는 `R2-CONFIRMATORY-`로 최초 holdout과 구분한다.
민감 source, 로그 형식, 별칭·컨테이너, private helper, 단순 분기,
안전한 예외 이벤트와 원문·traceback 노출을 함께 포함한다. 예외 사례에만 치우치지 않는다.
정답·메타데이터 계약과 미지원 검토 규칙은 최초 corpus와 같다.

새 표본 40개 전체와 지원 32개를 별도로 보고한다. 지원 위험 16개가 재현율 분모이고,
지원 안전 16개가 오탐률 분모다. 미지원 8개의 결과를 생략하지 않는다.
지원 표본의 오류·검토 필요 비율과 위험 allow도 별도로 보고한다.
진단에 사용한 최초 holdout을 새 확인용 성능과 합쳐 신선한 최종 평가로 표시하지 않는다.
전체 보유 표본은 140개지만 각 평가 단계의 분모와 공개 이력을 유지한다.

확인용 최초 동결 SHA-256:
`ce9243334113f2c1de010bb38c4b6d18b0d9bb4cd98e684e803068fa81f5a06e`

작성 시 40개 source의 Python 문법, 정확한 필드, 정답·지원 수, ID 유일성을 검사했다.
AST를 정규화하여 새 표본끼리와 원래 100개 사이의 구조적 source 중복이 없음을 확인했다.
원래 두 fixture의 동결 해시도 그대로임을 확인했다.
