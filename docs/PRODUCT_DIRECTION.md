# 제품 목적과 적용 범위

기준일: 2026-10-30. 사용자가 명시한 제품 목적을 반영한다. 현재 의도는 [INTENT.md](../INTENT.md)에 둔다.

## 제품이 해결하려는 문제

목표는 **다양한 공공 프로젝트에서 비개발자가 안전하게 바이브 코딩을 할 수 있도록 하는 것**이다. 여기서 바이브 코딩은 사용자가 자연어로 원하는 업무와 결과를 설명하고 AI가 만든 프로그램을 확인·수정하며 도구를 만드는 방식을 뜻한다.

핵심 사용자는 업무를 이해하지만 구현·보안의 세부 사항을 모두 판단하기 어려운 공공 업무 담당자다. 사용자가 직접 업무 도구를 만드는 과정에서 프로젝트에 필요한 기준을 놓치지 않고, 위험한 작업이나 미확인 상태를 알아볼 수 있도록 돕는다. 개발·보안 담당자는 실행 환경, 전문 판단과 운영 승인을 지원한다.

GovCode Harness는 **보안이 내재화된 개발 하네스**로서 요구 설명, AI의 코드 생성·수정, 실행과 검사, 담당자 검토, 결과 공유·운영 반영을 연결하는 제품을 지향한다. 이 전체 사용자 경험은 목표이며 현재 구현 완료를 뜻하지 않는다.

민원 API 개인정보 로깅은 공통 점검 흐름을 검증한 첫 사례다. 적용 업무를 민원 처리에 한정하지 않는다. 내부 업무 자동화, 자료 정리·보고, 현황 조회, 신청·접수 같은 공공 업무 도구는 향후 탐색할 사용 사례이며 현재 지원을 보장하는 목록은 아니다.

## 목표 사용자와 역할

| 역할 | 목표 경험 |
| --- | --- |
| 비개발자 제작자 | 만들고 싶은 업무 도구를 설명하고, AI가 만든 결과를 확인·수정하며 허용된 범위에서 시험한다. 다음 행동과 검토가 필요한 이유를 이해한다. |
| 개발·보안 지원 담당자 | 사용할 실행 환경과 기준을 준비하고, 자동 판단이 어려운 변경과 운영 반영을 검토한다. |
| 사업 책임자 | 제작 목적, 담당자, 시험 결과와 운영 승인 상태를 확인한다. |

비개발자의 참여를 가이드 열람·피드백 제출·개발 결과 검토로만 정의하지 않는다. 직접 제작하는 경험이 제품의 중심이다.

## 목표 사용자 흐름

1. 비개발자가 만들고 싶은 도구, 사용할 자료, 대상 사용자와 결과를 자연어로 설명한다.
2. 하네스가 프로젝트 조건과 필요한 확인 사항을 안내한다. 모르는 정보는 미확정으로 남긴다.
3. AI의 코드 생성·수정 과정에 프로젝트별 허용 범위와 점검 기준을 연결한다.
4. 사용자가 허용된 환경에서 결과를 시험한다. 문제를 발견하면 쉬운 설명과 다음 수정 행동을 제공한다.
5. 수정한 결과를 다시 검사하고, 자동 확인이 어려운 항목은 개발·보안 담당자의 검토로 연결한다.
6. 사용자가 시험 가능·검토 필요·운영 승인 상태와 근거를 이해한다.
7. 공유·운영 반영 전 필요한 승인과 자료를 확인하고, 이후 변경에도 다시 점검한다.

이는 설계 방향이다. 자연어 제작 화면, 코딩 에이전트 연결, 실행 권한 관리와 비개발자용 결과 설명의 제공 방식은 후속 설계가 필요하다. v0.9.0의 제한된 Python 로깅 검사는 이 전체 경험이나 다양한 업무의 안전성을 검증한 결과가 아니다.

## 다룰 수 있도록 확장할 영역

다음은 요구 수집·규정 팩·검사 어댑터를 설계할 **확장 후보**다. 특정 프로젝트에 모두 적용되는 의무 목록이 아니다.

| 영역 | 작업·산출물의 예 | 현재 상태 |
| --- | --- | --- |
| 개인정보·보안 | 로깅 최소화, 보안 점검, 통제 근거 | 제한된 Python 민원 API 로깅 사례를 합성 검증 |
| 접근성·사용성 | 접근성 점검과 보완 작업, 검토 기록 | 분야별 규정·검사 팩 미구현 |
| 개발 품질·시험 | 품질 기준, 필수 시험, 결함 조치 | 첫 사례의 기능·감사·개인정보 회귀 검증만 구현 |
| 표준·상호운용성 | 프로젝트별 표준·인터페이스 요구와 확인 자료 | 분야별 규정·검사 팩 미구현 |
| 사업 수행·산출물 | 단계별 필수 문서·검토·검수 자료 | 범용 산출물 요구 관리·검사 미구현 |
| 운영·기록·보존 | 운영 절차, 복구 확인, 보존·파기 근거 | 합성 증적 보관·복구 구현, 실제 기관 분류 미확정 |

법령상 의무·기관 규정·계약상 기준·권고 가이드·예시 정책을 구분한다. 적용성 검토와 정책 승인도 별도 단계다.

## 자동화와 담당자 판단

자동화 대상으로 규정의 구조화·추적, 수행 작업 안내, 결정적 검사, 허용한 수정과 산출물 지원, 재검사, 증적 묶음을 둔다.
규정 해석·기관 적용 판단·정책 승인·검수처럼 책임 있는 판단이 필요한 단계는 담당자와 근거를 명시한다.
전체 요구의 미검증 항목을 숨긴 채 개별 검사 통과율을 프로젝트 전체 준수율로 표시하지 않는다.

## 현재 구현과 다음 설계 단위

v0.9.0은 민원 API 개인정보 로깅 사례와 공통 정책·게이트·승인·증적·관리·격리 수정 기반을 제공한다. 320개 회귀 시험도 이 구현 범위의 검증이다.
기존 태그와 검증 기록은 유지한다. 이번 목적 정리는 새로운 범용 검사 기능의 구현 완료를 뜻하지 않는다.

다음 설계 단위는 다음 순서로 구체화한다. 일정과 구현 완료는 미확정이다.

1. 프로젝트 프로필과 적용 요구 목록: 대상·출처·버전·적용성·책임자.
2. 규정 팩 계약: 요구 → 수행 작업 → 산출물 → 자동 검사 또는 담당자 검토 → 증적.
3. 충족 현황: 전체 요구를 분모로 상태·미지원·미검증·승인 대기를 보여 주는 작업 안내.
4. 분야별 추가 Vertical Slice: 독립 정답·성공 기준을 정한 뒤 어댑터와 산출물 지원을 추가.
5. 변경 영향: 규정·프로젝트 조건·코드·산출물이 바뀌면 재검토 대상과 다음 작업을 안내.

## 비개발자 제작 경험을 검증할 다음 질문

비개발자가 실제로 만들고 싶은 첫 도구는 무엇인가, 어떤 자료·외부 연결·실행 권한이 필요한가, 어떤 결과를 스스로 판단할 수 있고 어디서 전문가의 도움이 필요한가를 확인해야 한다. 기존 프로필·규정 팩 기반 위에서 자연어 제작 과정과 점검·수정·검토를 연결하는 사용성 검증이 필요하다. 규정의 적용 대상 관리만으로 안전한 바이브 코딩 경험이 완성됐다고 판단하지 않는다.
